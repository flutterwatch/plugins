## How this differs from sqflite_darwin

sqflite_darwin is a method-channel plugin around FMDB. Method channels do
not run on watchOS, and FMDB is a wrapper the watch does not need, so this
package keeps none of that native code:

- `lib/src/sqlite3.dart` binds the part of SQLite's C API sqflite needs
  (`sqlite3_open_v2`, `_prepare_v2`, `_step`, the `_bind_*` and `_column_*`
  functions, `_changes`, `_last_insert_rowid`, `_get_autocommit`,
  `_busy_timeout`, the error calls). Arguments bind as sqflite_darwin binds
  them: a `bool` as 1 or 0, a `Uint8List` or plain `List<int>` as a blob.
  Each connection waits up to 2 seconds for another connection's lock,
  FMDB's default on iOS. On the watch the functions resolve from the
  process, because `watchos/Package.swift` links the system `libsqlite3`;
  host tests have the background isolate open the host's system library by
  path instead, so the same code runs real SQL there.
- `lib/src/handler.dart` answers sqflite's method protocol: the same
  methods, arguments and results the method channel carries on iOS. It is
  adapted from sqflite_common_ffi's `lib/src/sqflite_ffi_impl.dart`, the
  protocol's reference implementation outside a method channel, and carries
  its copyright notice. That covers transaction ids (a call from outside
  the open transaction waits for it), `transactionClosed` when SQLite rolls a
  transaction back, paged cursors, batches with `continueOnError`, and
  single-instance databases, never for `:memory:`, as in sqflite_darwin.
- `lib/src/worker.dart` runs the handler on a background isolate, as
  sqflite_common_ffi's `databaseFactoryFfi` does, where sqflite_darwin gives
  each database a dispatch queue of its own. The first call starts the
  isolate, and every database shares it. The handler and what it holds
  (databases, transactions, cursors) live there; each call crosses as a
  message, and a `SqfliteDatabaseException` crosses back as its message,
  details, result code and `transactionClosed`. So the 2-second lock wait
  blocks that isolate, not the UI, and two connections to one file cannot
  wait each other out (see the README). It is adapted from
  sqflite_common_ffi's `lib/src/isolate_io.dart` and `lib/src/method_call.dart`,
  and carries its copyright notice.
- `watchos/Classes/sqflite_watchos_ffi.m` has two helpers: the Documents
  directory, and `sqlite3_libversion()`, which also keeps `libsqlite3` linked.
- sqflite federates through sqflite_common's default factory. `SqfliteWatchos`
  extends `SqflitePlatform`, as `SqfliteDarwin` does, and its `registerWith`
  sets `databaseFactoryOrNull` to `databaseFactoryWatchos`, a factory from
  sqflite_common's `buildDatabaseFactory`, as sqflite_darwin sets its
  method-channel factory. `buildDatabaseFactory` and
  `SqfliteDatabaseException` come from sqflite_common's `src/` libraries,
  which sqflite_common_ffi imports the same way; `src/` is not public API, so
  `sqflite_common: ">=2.5.14 <2.6.0"` stops below the next minor.

The one API the port tool flagged, `UIDevice` (the platform version), is
replaced by `Platform.operatingSystemVersion`.

## Example

`example/` is sqflite 2.4.5's own example (`sqflite/example` in
tekartik/sqflite): `lib/main.dart` and `lib/compat_test_run.dart` are
upstream's, unchanged. Its pages come from `sqflite_example_common`, which is
not published on pub.dev. The watch deviations are both in
`example/pubspec.yaml`:

| Change | Why |
|---|---|
| `sqflite_example_common` is pinned with `ref` to tekartik/sqflite `21d2b8d` | it is not on pub.dev, and upstream's pubspec takes it from the repository's default branch, which can move under the example; `21d2b8d` is the commit of sqflite 2.4.5 |
| `sqflite_watchos` is added | the watch implementation |

The other dependencies are upstream's, each with a caret on the version it
ran with here, as this repository's CI asks.
`example/integration_test/sqflite_test.dart` is upstream's test, unchanged
but for the formatting this repo's CI checks.

On the watchOS 27.0 Simulator (Series 12, 46mm, 2026-10-30) the example
started with no error in its console (first frame 0.8 s after the engine
ran, built with `--dart-define=flutter.inspector.structuredErrors=false`),
and its list of test pages fits the screen. Its "Raw tests" page ran
upstream's SQL checks, against SQLite 3.54.0: every result seen while
scrolling the page was a pass, and the console showed no failure. The
official integration test passed (14 tests).
